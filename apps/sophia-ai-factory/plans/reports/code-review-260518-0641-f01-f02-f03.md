## F01 — Per-account failed-login lockout

### Correctness
- **Threshold 5 / lock 24h:** sensible default for ASVS L2 (NIST SP 800-63B § 5.2.2 recommends ≤ 100 attempts; 5 is conservative).
- **Reset semantics:** `resetFailedLogin` clears both `failed_login_attempts → 0` AND `locked_until → NULL` — correct.
- **Lock check order:** `verifyWithLockout` checks lock BEFORE invoking password verifier (line 64–71). Cannot be probed for valid passwords on a locked account. ✅
- **Throw-handling:** if the password verifier itself throws (e.g. bcrypt internal error), counter is incremented (line 76–80). This is the correct fail-closed posture.
- **Independence from IP:** lock is keyed on `userId` only — confirmed by test "lock is independent of IP".

### SQL safety
- **All queries parameterized via D1 `prepare().bind()`** — no string interpolation of user data. ✅
- **Three queries:**
  - `SELECT failed_login_attempts, locked_until FROM "user" WHERE id = ?1` ✅
  - `UPDATE "user" SET failed_login_attempts = ?1, locked_until = ?2 WHERE id = ?3` ✅
  - `UPDATE "user" SET failed_login_attempts = 0, locked_until = NULL WHERE id = ?1` ✅
- `"user"` is quoted (Better Auth reserved name). Correct for D1/SQLite.

### Migration 0114
- `ALTER TABLE "user" ADD COLUMN failed_login_attempts INTEGER NOT NULL DEFAULT 0;` — safe for existing rows (default backfills); D1 supports `ADD COLUMN` without rewrite. ✅
- `locked_until INTEGER` nullable — correct (NULL = not locked).
- **Partial index** `WHERE locked_until IS NOT NULL` — efficient (most users not locked, index is small). ✅
- **Reversibility:** SQLite `ALTER TABLE ... DROP COLUMN` is supported (SQLite ≥ 3.35, D1 is current). No rollback migration provided — minor, not blocking.

### account-lockout-hook.ts TODO
The TODO documents a real Better Auth limitation (`verify({ hash, password })` does not receive `userId`). The wrapper `verifyWithLockout` is fully functional and tested; it just isn't wired into Better Auth's `emailAndPassword` provider yet. This is **acceptable as a transitional state**: the building block is production-ready and can be invoked from any custom sign-in route, but the canonical Better Auth path is not yet protected. **Not dead code**, but the protection is only active on callers that explicitly opt in.

→ **Note:** Until wired in, F01 lockout is NOT actually enforced on the main Better Auth `/api/auth/sign-in/email` endpoint. The ASVS V2.2.2 requirement is technically only half-shipped. A follow-up phase is needed to either wrap the Better Auth route or upstream a `beforeSignIn` hook PR.

## F02 — Admin re-authentication challenge

### HMAC sign / verify
- Uses `crypto.subtle.importKey('raw', ..., {name:'HMAC', hash:'SHA-256'}, false, ['sign','verify'])` — correct Web Crypto usage on CF Workers.
- Token format: `base64url(payload).base64url(HMAC(payload))` — standard JWT-like compact form, without JWT header (acceptable since type is fixed).
- **Signing input:** `payloadB64` (the base64url-encoded JSON), not raw JSON — protects against canonicalization issues. ✅
- **base64url ↔ base64 round-trip** correctly handles padding (line 89–90).

### Constant-time comparison
- `crypto.subtle.verify` is **specified to be constant-time** by the Web Crypto spec (W3C Web Crypto §11.1). Comparing the computed MAC to the provided signature internally — no manual `===` on hex digests. ✅

### Cookie attributes (admin-challenge/route.ts line 156–162)
```ts
httpOnly: true,
secure: true,
sameSite: 'strict',
maxAge: 300, // 5 minutes
path: '/',
```
All four attributes correct per ASVS V3.4.1 / V3.4.2 / V3.4.3. ✅

### Password / MFA verifier
- `verifyPassword` from `@/tree/crypto/password-hash` — confirmed real PBKDF2 verifier (line 22 of password-hash.ts). NOT a stub.
- `verifyTotp` from `@/seed/auth/mfa/totp-service` — real TOTP verifier with ±1 window. NOT a stub.
- **Caveat documented in code (line 140–142):** `verifyTotp` doesn't handle `is_encrypted=1` rows. Author flagged this with a comment. Acceptable for current admin user base (likely no encrypted TOTP yet) but a follow-up is needed if admin TOTP secrets get encrypted.

### Gate placement (bulk-generate/route.ts)
Order: `requireAdmin` (line 49–51) → `requireRecentAuth` (line 54–60) → `rateLimit` → body parse → business logic. ✅
- Admin gate first means anonymous requests get 401 without leaking that the route requires recent auth.
- Re-auth gate before rate-limit means a brute-force probe of the challenge is bounded by the admin session itself.

### Cookie parse fix (require-admin.ts line 68–74)
```ts
request.headers.get('cookie')?.split(';').find(c => c.trim().startsWith('admin_challenge_token='))?.split('=').slice(1).join('=')
```
- `split('=').slice(1).join('=')` correctly handles `=` in base64url-encoded values. ✅
- **However:** if a base64url-encoded value contains literal `=` padding chars (the code at line 44–45 strips padding via `.replace(/=/g, '')`, so this shouldn't occur in practice), parsing is still robust.
- **URL-encoded values:** Next.js's `cookies.set()` does NOT URL-encode by default for ASCII-safe values, and base64url is ASCII-safe (chars: `A-Za-z0-9-_`). No decoding needed. ✅
- **Edge case:** cookie order matters in `find()`. If `admin_challenge_token=abc` is preceded by `not_admin_challenge_token=xyz`, `startsWith('admin_challenge_token=')` could match the latter as a substring. **MINOR:** `startsWith` after `trim()` requires the cookie to start exactly with the name. Since cookie names don't contain spaces or special chars, and `trim()` strips leading whitespace, the only collision risk is if another cookie name ends with `admin_challenge_token`. Unlikely but theoretically possible. Recommend changing to `startsWith('admin_challenge_token=')` with an explicit `=` separator — which is already done. ✅

→ **No issue**; original concern addressed by `=` suffix in the prefix.

### Replay window
5-minute Max-Age + HMAC payload `issuedAt` check (line 121–123) — token cannot be replayed past 5 minutes, and tampering with `issuedAt` fails HMAC verify. ✅

### Open question (not blocking)
The challenge token does not include a `nonce` or `jti`, so within the 5-minute window a token can be replayed multiple times. For "bulk generate promo codes" this is mostly fine (re-auth is meant to confirm intent at the start of a session of admin work). For more sensitive operations (e.g. transferring funds), a single-use nonce would be stronger. Not required by ASVS L2 V3.5.1.
