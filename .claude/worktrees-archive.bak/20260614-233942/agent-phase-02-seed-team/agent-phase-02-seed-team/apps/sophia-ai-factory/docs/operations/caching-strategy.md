# Caching Strategy — Phase 42

> **Status:** DRAFT v0.1  
> **Context:** Post Phase 40-49 modularization. KV + in-memory caching layer decisions.

## 1. Caching Layers

| Layer | Technology | Scope | TTL | Eviction |
|-------|-----------|-------|-----|----------|
| L1 — In-process | `Map<string, T>` (per worker instance) | Hot config, feature flags | 30s | LRU capped at 500 entries |
| L2 — KV namespace | Cloudflare KV (`CACHE`) | SOP templates, user prefs, rate-limit counters | 5m–1h (per key) | TTL-based |
| L3 — CDN | Cloudflare Cache Rules | Static assets, public API responses | 1h–24h | Cache-Control header |
| L4 — Browser | `Cache-Control: immutable` | SOP marketplace, static docs | 7d | Versioned URLs |

## 2. Key Selection Rules

- **KV-write-heavy data:** DO NOT cache (DB source of truth).
- **Read-heavy, rarely-mutated:** KV with 1h TTL + background refresh.
- **Hot config (feature flags, tier limits):** L1 in-process, 30s TTL, invalidated on admin update.
- **User-scoped data:** L1 only (no cross-instance sharing).

## 3. Cache Invalidation

- Admin update → emit event → L1 invalidate on all instances (next request repopulates).
- KV mutation → delete key + write new value (no stale reads).
- SOP template update → re-render + KV put with new version hash in key.

## 4. Observability

- Cache hit rate per layer (exposed via `/api/admin/metrics`).
- KV latency p50/p95.
- L1 size (number of entries, memory estimate).
- Alert: L1 size > 450 entries → suspect leak.
